# 站点接入与持续回补规范

本规范用于在统一 `SiteAdapter` 架构中接入有分页列表的数据泄露来源。目标是及时发现新情报，同时可恢复地补齐历史详情。新站点复用分页调度、待抓队列与任务执行入口，只实现本站请求、解析和落库差异。

## 默认预算与统计口径

| 配置 | 默认值 | 作用 |
| --- | ---: | --- |
| `recent_pages_per_run` | 1 | 每个分区每轮优先检查的最新页数 |
| `backfill_pages_per_run` | 5 | 整个站点每轮历史页预算，按分区公平分配 |
| `frontier_max_pending` | 500 | 未完成详情积压阈值，包含已经领取的任务 |
| `max_detail_pages_per_run` | 沿用本站配置 | 每次补充派发的领取额度 |
| `max_concurrent_details` | 沿用本站配置 | 同站同时执行的详情上限 |

历史游标按站点和分区保存，进程重启后从保存的页码继续，已完成的游标不会在下一轮自动从第二页重扫。最新页持续检查；发现需要处理的最新内容时暂停历史发现，否则历史页预算受剩余派发窗口和未完成候选数限制。阈值是暂停历史发现的水位；最新页或单页批量发现可以让数据库待抓候选超过水位，候选仍须完整保存。

每站派发窗口固定为 `2 * max_concurrent_details`，在同一数据库事务内检查窗口和领取候选。最新候选优先，历史任务使用较低 broker 优先级；详情完成后补充空位，不必等待下一轮列表扫描。

`pending` 是尚未完成且未被有效领取的任务，包含等待重试的任务；`inflight` 包含派发预留、已入队和正在执行的任务；`completed` 是队列中当前已完成的任务。它们不表示源站总条数，也不等同于去重后的新增情报条数。分页到末页仅表示列表发现扫描完成，详情仍需逐条成功入库。

## 适配器接入

1. 在 `sites/<site>.py` 实现列表和详情解析，提供稳定主题标识、标题、来源 URL、所属分区及正文相关版本信息。
2. 在 `adapters/<site>.py` 实现现有 `SiteAdapter` 接口，并以 `supports_frontier = True` 声明使用持久待抓机制。MyBB 论坛复用 [collect_forum_seed](./src/darkweb_collector/adapters/pagination.py)，其他分页 API 复用同文件的 `collect_paginated_seed`，保留分页元数据；不要在适配器内复制一套队列调度。
3. `plan_details` 返回已发现且符合采集范围的详情候选，不提前按详情额度截断。执行入口持久保存候选、按分区公平领取，再消耗本轮额度。
4. 在 `adapters/registry.py` 注册，在 `sites.yaml` 设置实际入口、分页预算、详情预算和抓取方式。登录、代理和浏览器状态继续使用现有统一配置。
5. 先用本地 HTML/API 样本和隔离数据库验证，再进行有限页面的线上验证。新站点必须同步在实际站点管理页面展示其状态与回补进度。

分页请求须保留站点原有的排序和过滤参数，替换页码时不能丢失这些参数。论坛优先按最新创建时间排序；源站只支持其他排序时，需说明翻页过程中内容移动带来的覆盖边界。同一页面的置顶主题和翻页重叠应按稳定主题标识去重。

`collect_paginated_seed(site_name, config, fetch_page, plan_details=adapter.plan_details)` 的分页回调接受 `(source_url, page, collected_at)`，返回 `(parsed_section, raw_page, has_more, id_signature, page_url)`。`plan_details` 复用适配器原有的版本和证据去重规则，判断最新页是否还有实际需要处理的内容。`parsed_section` 至少包含 `section` 和 `topics`，主题包含 `full_url`；`source_count` 记录过滤前条数，避免把全页被过滤误判为末页。返回的 `SeedResult.metadata.cursor_updates` 由执行入口在候选入库后写入；适配器不要提前保存游标。

MyBB 论坛对每次请求返回的主题完整解析，按请求页数控制发现量，避免 `max_topics_per_run` 截断后永久漏掉同页尾部主题。长安继续将该字段作为 API 请求的每页大小；如果服务器返回更小的分页大小，也继续根据实际响应和总数翻页。

每个候选的 `DetailTask.metadata` 包含 `source_version`、`section` 和 `discovery_lane`（`recent` 或 `backfill`），以及本站需要的主题 ID、镜像文件名等。详情 `persist` 必须接受可选 `connection`；调用者提供连接时，不得自行提交或关闭，由执行入口将租约检查、详情写入和版本完成放在同一事务。`frontier_artifact_only` 任务通过 `restore_detail_artifacts` 复用已保存且与数据库正文哈希一致的 JSON/HTML 补充截图，不重复请求正文。截图仍遵循原有浏览器队列和并发限制。

只有页面成功解析、候选已经持久保存后才能推进游标。登录页、验证码页、请求失败和异常空响应不能当作末页。根据可信的分页元数据确认末页；重复页面签名用于防止源站忽略页码导致无限扫描。单分区失败应保留游标，让其他分区仍可继续。

## 版本、完成与恢复

发现版本 `observed_version` 表示最近观察到的内容版本，成功版本 `fetched_version` 表示已经入库的版本。领取任务必须绑定当时的版本；抓取期间发现新版时，旧任务完成只能确认旧版，新版仍留在待抓队列。这些状态由 [crawl_frontier.py](./src/darkweb_collector/crawl_frontier.py) 的 `observe_frontier`、`claim_frontier` 和 `complete_frontier` 管理。

内容哈希应覆盖会影响情报分析的稳定字段，如标题、正文摘要、附件标识和有意义的更新时间。浏览量、点赞数等展示计数不触发重新抓取正文；价格、分类等字段是否影响版本应由本站情报需求决定。长安列表的浏览量变化不应耗尽详情额度。

详情成功持久化后才确认对应版本完成。重复完成通知须幂等，晚到的旧任务不得覆盖新任务的状态。派发预留为 60 秒；发布成功后进入 `queued`，排队等待不会因运行租约到期而重复派发。取得执行槽位后才进入 `running` 并开始运行租约。运行租约到期不能作为存活进程已经退出的依据：受监督任务必须先确认其整个进程树退出，再回收任务、待抓记录和站点执行名额。过期的排队记录不再占据派发窗口，迟到的旧消息只结束自己的未完成记录。派发失败只释放仍属于该次派发的预留，不能覆盖已经开始或完成的快 worker。浏览器证据尚未补齐时须保留补全状态，不能把正文已获取误判为全部证据完成。

旧格式已发布的积压先标记为 `legacy_queued`，首次交付时在同一事务内退回数据库 `pending` 并结束旧投递记录，再确认原消息。版本和证据进度保留，旧 token 失效；历史任务随后按新窗口低优先派发，不循环投递 ETA 重试。事务失败时保留原消息重排。迁移中的存量仍计入 `inflight`，新派发窗口单独受并发上限约束。

优先使用能够稳定获取有效正文的 HTTP/API 路径。只有实际需要页面渲染或补充浏览器证据的请求才消耗浏览器资源。正文与截图具备独立执行能力后，截图必须绑定内容版本；不得为缺少截图而重复更新已入库正文版本。

## 全站失败处理与重试预算

全部已注册适配器均通过公共详情入口管理持久重试预算和执行所有权，包括没有使用分页待抓机制的来源。适配器使用 `CollectionFailure` 提供明确原因；普通空响应、未知页面、HTTP 404/410 和解析失败不能直接判断为帖子删除。`NoGoods`/4007 仅由长安适配器解释；论坛删除判断需要匹配本站明确的错误模板。登录、验证码、权限提示不能被当作有效正文，正文引用这些提示的正常文章也不能被误判。

| 原因 | 默认处理 |
| --- | --- |
| 明确不可用、单帖权限限制 | 目标冷却 24 小时后低频复查，保留原正文和证据 |
| 登录失效、验证码拦截、限流 | 对应站点冷却 30 分钟；单帖权限不足不暂停其他帖子 |
| 网络或超时 | 前两次失败分别等待 60 秒、300 秒；连续三次失败后等待 1 小时 |
| 空正文、解析失败或未知结果 | 首次等待 15 分钟，再次失败等待 1 小时，不清空已有正文 |
| 正文有效但缺少截图 | 正文先提交，标记 `partial`，1 小时后只补截图 |

失败恢复期间，每个站点/目标地址的主文档请求共用每小时 6 次的持久预算，成功入库后归零。HTTP、代理、浏览器备用路径均计入，适配器不能叠加独立重复循环绕过预算。恢复轮次仍可以使用有界的备用路径；持续失败限制的是轮次频率，避免永远只尝试第一条路径。观察时间、浏览量等字段变化不能清零失败请求预算；真实来源版本变化可以提前复查，但仍受该预算约束。人工强制运行会清除未在执行目标的冷却和预算，不抢占存活任务。

冷却中的记录仍保留在待抓清单，但不作为当前可执行新增任务，也不占历史发现的可执行容量。存在可执行新增时先处理新增；没有可执行新增时，历史发现仍受小窗口和配置页数限制。

Windows 启动器使用受监督的 `solo` 消费进程。详情总时限默认公网 300 秒、Onion 600 秒；`detail_task_timeout_seconds` 可以设置 60–900 秒。站点执行槽的 TTL 至少覆盖总时限加 90 秒清理余量，同时使用数据库站点准入锁防止消息服务租约过期后产生重叠执行。守护进程每 15 秒检查，Windows Job Object 收容浏览器子孙进程；确认全部退出后才恢复任务。清理或数据库/消息服务恢复失败时保留日志，阻止替换进程。

控制台确认没有队列消费者时返回 `worker_unavailable`，不启动绕过守护的线程或进程池。显式 CLI 单次调用仍采用传输超时和持久请求预算，不具备队列守护进程的强制退出保证。

数据库初始化自动增加 `crawl_detail_control`、`crawl_site_control`、`crawl_detail_results` 及必要索引，不删除历史数据。有效正文持久化、任务完成和待抓版本确认使用同一事务；空结果或没有实际正文写入的任务不能记为成功。`/api/jobs` 的 `detail_yield_24h` 分别提供新建、更新、未变化的原始正文记录数，以及证据待补任务数；这些数值不等于标准化后的新增情报数，也不追溯改写升级前的任务历史。

详情 JSON 中的 `_collector_artifacts_complete` 仅记录本地证据状态，不参加内容哈希。新正文截图失败时保留旧 PNG，但显式记录未完成，避免下一轮把旧图误认为新版本截图已完成。

## 验证与效率评估

接入至少验证：首页到后续页确实发生网络请求；重启后游标继续；置顶及跨页重叠不重复入库；某分区失败后其他分区仍推进；详情额度不足时剩余候选不丢失；前面的任务处于冷却期时后续任务仍可领取；派发失败、租约过期及重复完成均能恢复；抓取中的版本变化不会被旧任务确认；积压达到阈值仍检查最新页。

性能同时记录每小时去重后的有效新增或实质更新、发现到可搜索的延迟、队列等待时间、请求成功率和证据完整率。列表扫描条数、任务执行次数及数据库更新次数不能替代有效情报产出。

增加历史页预算会加快旧数据覆盖，也会增加源站请求和详情积压；增加最新页预算适合更新速度超过轮询间隔的分区。先用运行数据调整预算，再调整 worker 和出口容量。这套机制提供可持续的默认策略，不能保证所有站点上的绝对最大效率。支持增量 API、站点地图、时间游标或少量公告的来源应优先使用其更合适的发现接口，并复用同一版本和恢复语义。
